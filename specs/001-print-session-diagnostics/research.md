# Research: Диагностика и безопасная остановка сессии печати

**Feature**: `001-print-session-diagnostics` | **Date**: 2026-11-02

Фаза 0. Все `NEEDS CLARIFICATION` из Technical Context закрыты: неоднозначности
спеки сняты в `spec.md` (сессия Clarifications 2026-11-02), технические —
исследованием кода ниже. Формат каждого пункта: решение → обоснование →

## R1. Где хранить журнал: отдельная область EEPROM, а не `SettingsData`

**Решение.** Отдельная область 768 байт в конце EEPROM:
`PRINT_JOURNAL_ADDR = MARLIN_EEPROM_SIZE - 768` (на этой плате `0x1000`, т.е.
`0xD00..0xFFF`), со своим заголовком (magic, версия, указатель, счётчик, CRC16)
и per-entry CRC8. Доступ — напрямую через `persistentStore`
(`HAL/shared/eeprom_api.h`), как это уже делает UBL для мешей
(`module/settings.cpp`, запись `persistentStore.write_data(pos, src, size, &crc)`).

**Обоснование.**
- `SettingsData` и `EEPROM_VERSION "V87"` остаются нетронутыми → пользовательские
  настройки не сбрасываются, `Initialize EEPROM` не требуется (FR-012, принцип
  VI конституции).
- Форк включает `EEPROM_INIT_NOW` (`Configuration.h:2261`), а `build_hash`
  считается из `__DATE__ __TIME__` (`settings.cpp:733-738`). Любая пересборка
  сбрасывает `SettingsData`; журнал вне этого блока переживает перепрошивку —
  иначе разбор дефекта после обновления прошивки терял бы историю.
- Область журнала не участвует в `save()`/`load()`/`M500`/`M501`/`M502`,
  поэтому ошибка CRC журнала никогда не приводит к `settings.reset()`.

**Отклонено.**
- *Поле внутри `SettingsData`*: требует смены `EEPROM_VERSION` (иначе
  «EEPROM datasize error»), увеличивает diff в общем файле и теряет журнал при
  каждой пересборке из-за `EEPROM_INIT_NOW`.
- *Файл на SD*: карта может быть изъята/сбойна именно в момент останова
  (US1 сценарий 5); спека прямо ограничивает первую версию EEPROM/экраном,
  полный лог на носителе — вне области.
- *Flash-эмуляция EEPROM*: на этой плате выбран `I2C_EEPROM`
  (`pins/stm32f4/pins_MKS_ROBIN_NANO_V3_common.h:37-42`), `FLASH_EEPROM_EMULATION`
  закомментирован; менять носитель ради журнала — регрессия принципа III.

## R2. Формат записи и стоимость

**Решение.** Кольцевой буфер на 16 слотов; в заголовке — `head` и `count`.
Запись события = один слот (28 байт) + заголовок (12 байт). CRC8 на запись,
CRC16 на заголовок. Заголовок при повреждении восстанавливается сканированием
слотов (выбирается слот с максимальным `seq`), повреждённая запись
пропускается, остальные читаются.

**Обоснование.**
- I²C-EEPROM пишется побайтово: `eeprom_write_byte()` → `delay(EEPROM_WRITE_DELAY)`
  = 5 мс, плюс 2 мс в цикле (`HAL/shared/eeprom_if_i2c.cpp:51-92`,
  `HAL/STM32/eeprom_wired.cpp:47-64`). Но запись идёт **только для изменённых
  байт** (`if (v != eeprom_read_byte(p))`, строка 52), поэтому полный массив
  каждый раз не переписывается.
- 28 + 12 = 40 байт → ≈ 280 мс на событие, один раз в момент останова, когда
  движение уже прекращено. Для сравнения: `safe_delay` в том же цикле не даёт
  сработать watchdog (4 с, `HAL/STM32/HAL.cpp:147-164`).
- Per-entry CRC8 (а не общий CRC16 на весь журнал) нужен для edge case
  «пропадание питания в момент записи»: теряется максимум одна запись,
  остальные 15 читаются (FR-008, SC-002, SC-003).

**Отклонено.** Общий CRC на всю область (одна битая запись обнуляет журнал);
запись всего массива (30 с на цикл — недопустимо).

## R3. Активная сессия и обнаружение сброса

**Решение.** Отдельный маленький блок «активная сессия» — два чередующихся
слота по 32 байта (seq + CRC8 + содержимое). Содержимое: magic, seq, этап,
имя файла (8.3), контрольная длительность (с), процент. Пишется:
- при старте печати (`startOrResumeJob()`);
- при паузе/резюме и смене этапа;
- контрольной записью раз в `FB_G6_PRINT_JOURNAL_CHECKPOINT_S` (300 с);
- очищается (seq++ и `active = false`) при штатном завершении и при отмене.

На старте прошивки валидный слот с `active = true` означает, что предыдущая
сессия не закончилась → синтезируется событие `CAUSE_RESET` с подтипом из
`hal.get_reset_source()` и контрольной длительностью.

**Обоснование.**
- Сброс (watchdog/питание) не даёт возможности выполнить код останова, поэтому
  факт «печать была активна» обязан быть уже на диске (US1 сценарий 2).
- Два слота нужны из-за отсутствия атомарной записи: сбой посреди записи
  портит только один слот, второй остаётся валидным (R2).
- Контрольная длительность даёт приблизительную длительность для записи после
  сброса (точное значение получить нельзя: RTC на плате нет, `millis()`
  обнуляется). Это осознанное уточнение к FR-001 — фиксируется в
  `contracts/journal-storage.md`.

**Отклонено.** Запись длительности каждую секунду/процент (износ + тормоза
печати); хранение только «флага печати» (нет длительности, SC-004 хуже).

## R4. Таксономия причин: стабильные коды с группами

**Решение.** Числовые коды с фиксированными диапазонами:
`0x00` завершено; `0x10–0x1F` отмена/внешняя команда; `0x20–0x2F` носитель;
`0x30–0x3F` сброс (подтип watchdog/питание/программный-кнопочный);
`0x40–0x4F` авария (термозащита, M112, прочее); `0x50–0x5F` внутренняя
остановка (ошибка probe и т.п.); `0x7F` неизвестно. Полная таблица —
`contracts/stop-reasons.md`.

**Обоснование.** FR-010: коды стабильны и расширяемы без изменения выданных
значений; группировка по старшей тетраде позволяет добавлять причины внутри
группы, не ломая ни журнал, ни UI (UI показывает группу, если точный код
неизвестен).

**Отклонено.** Строковые причины в EEPROM (дорого по байтам и не локализуется);
перечисление без диапазонов (любое добавление сдвигает значения).

## R5. Единая воронка источника останова

**Решение.** Метка источника — короткоживущая переменная модуля
(`StopSource pending_source`), выставляемая **перед** вызовом останова, и
потребляемая (с обнулением в `SOURCE_UNKNOWN`) в `abortSDPrinting()`.
Точки установки (5):

| Точка | Файл:строка | Источник |
| --- | --- | --- |
| `STOP_PRINT` на TFT | `lcd/tft/touch.cpp:428-432` | `SOURCE_LOCAL_UI` |
| подтверждение в меню | `lcd/menu/menu_main.cpp:305-312` | `SOURCE_LOCAL_UI` |
| WiFi `M26` | `module/wifi/wifi.cpp:1060-1068` | `SOURCE_NETWORK` |
| `M524` (G-code и emergency-парсер) | `gcode/sd/M524.cpp:44-48`, `module/temperature.cpp:1871-1875` | `SOURCE_HOST` |
| извлечение карты | `sd/cardreader.cpp:538-551` (`release()`) | `SOURCE_MEDIA` |

**Обоснование.** `CardReader::abortFilePrintSoon()` (`sd/cardreader.h:172`) —
общая точка всех отмен, но у неё нет параметра, а её вызывают несколько UI.
Менять сигнатуру в общем файле — лишний diff и риск для апстрим-мержа
(принцип II). Метка рядом с вызовом даёт тот же результат при 1 строке на
точку.

**Отклонено.** Параметр в `abortFilePrintSoon(src)` (правка общего API Marlin);
определение источника «по стеку» (невозможно на AVR-стиле C++ без RTTI);
источник из `card.flag` (флаги — битовое поле, расширять его под кастому хуже,
чем отдельная переменная).

## R6. Штатное завершение

**Решение.** Запись `CAUSE_COMPLETED` в `MarlinCore.cpp::finishSDPrinting()`
(строки 385-393), сразу после успешной постановки `M1001` в очередь; там же
очищается активная сессия и ставится `ui.screen_num = 3` (существующий экран
«Printing Finished»).

**Обоснование.** `marlin_state == MF_SD_COMPLETE` выставляется в
`CardReader::fileHasFinished()` (`sd/cardreader.cpp:1296-1312`), а
`finishSDPrinting()` — единственное место, где завершение подтверждено
обработкой `M1001`. Запись здесь гарантирует, что «завершено» и «сброс» не
задваиваются (edge case спеки): после записи активная сессия уже погашена, и
следующий сброс не создаст ложное событие.

**Отклонено.** Фиксация в `card.fileHasFinished()` (там ещё нет `M1001`, печать
может сорваться на нём) и в `M1001` (общий gcode-файл, вызывается в т.ч.
вручную).

## R7. Аварийная остановка: best-effort запись в `kill()`

**Решение.** В `kill()` (`MarlinCore.cpp:898-922`) после
`thermalManager.disable_all_heaters()` вызвать `print_session.note_emergency()`:
он пишет `emergency_cause`/`emergency_source`/`FLAG_EMERGENCY` в RAM и
`noinit`-запись `EmergencyRecord` (`magic`+`crc8`), затем выполняет best-effort
`append(StopEvent)` в EEPROM. Если запись не удалась, `init()` при следующей
загрузке синтезирует событие из `noinit`-записи.

**Обоснование.**
- `minkill()` (`:924-964`) заканчивается `cli()` и далее либо `hal.reboot()`,
  либо бесконечным `for (;;) hal.watchdog_refresh();` — вернуться в `idle()` и
  «отложенно» записать событие невозможно (это подтверждено кодом, поэтому
  вариант «запись из `task()`» отклонён).
- `loud_kill()` вызывается из `_temp_error()` в нормальном контексте
  (`updateTemperaturesFromRawValues()`/`Temperature::task()`), а не из ISR,
  поэтому блокирующая запись EEPROM технически возможна; ограничение — риск
  просадки питания при аварии, а не ISR.
- `noinit`-запись (16 Б) переживает программный сброс (`hal.reboot()`, кнопка
  KILL) и разбирается на загрузке; при снятии питания она теряется, и тогда
  синтезируется `CAUSE_RESET_POWER` с `FLAG_EMERGENCY_DETAIL_LOST`.
- Подтип аварии выставляется меткой перед `kill()`: `loud_kill()` в
  `module/temperature.cpp:1243-1262` → «термозащита»; обработчик M112
  (`temperature.cpp:1862-1863`, `wifi.cpp:2080`) → «M112»; по умолчанию —
  «авария, причина не уточнена».

**Риск и его принятие.** Основной путь — прямая best-effort запись события в
`kill()`; `noinit` остаётся fallback на случай, если запись не завершилась.
Сохранность `.noinit`-секции в сборке STM32duino нужно доказать: проверить,
что секция не обнуляется стартовым кодом (магическое слово + `crc8`), и
подтвердить на принтере сценарием S10. Если механизм не подтверждён и прямая
запись не удалась — деталь аварии не сохраняется, при загрузке фиксируется
`CAUSE_RESET_POWER` + `FLAG_EMERGENCY_DETAIL_LOST`.

**Отклонено.** Только `noinit` без прямой записи (деталь теряется при снятии
питания); отложенная запись из `idle()` (невозможна — машина уже остановлена);
запись в `minkill()` после `cli()` (хуже: прерывания уже выключены).

## R8. Тип сброса: переиспользовать `hal.get_reset_source()`

**Решение.** В `MarlinCore.cpp:1155` значение `const byte mcu = hal.get_reset_source()`
сохраняется в модуль **до** `hal.clear_reset_source()` (строка 1156), затем
маппится: `RST_WATCHDOG` → watchdog, `RST_POWER_ON` → питание,
`RST_SOFTWARE`/`RST_EXTERNAL` → программный/кнопочный.

**Обоснование.** Механизм уже реализован в `HAL/STM32/HAL.cpp:117-141`
(`__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST/SFTRST/PINRST/PORRST)`), константы —
`HAL/shared/Marduino.h:68-73`. Новый драйвер не нужен; отсутствует только
сохранение значения (сейчас это локальная переменная `setup()`), добавляется
одна строка.

Замечание: штатная реализация STM32 не выставляет отдельный флаг brownout;
он проявляется как `RST_POWER_ON`/`RST_PINRST`. В контракте это отражено: подтип
«питание» означает «включение/просадка питания», а не отдельный флаг.

**Отклонено.** Собственное чтение `RCC->CSR` в модуле (дублирование HAL,
принцип II); хранение «последнего состояния» только в RAM (теряется при reset).

## R9. Модальное окно причины в `TFT_COLOR_UI`

**Решение.** Отдельный экран (`screenFunc_t`), открываемый как
`ui.push_current_screen(); ui.goto_screen(MarlinUI::stop_reason_screen);`
с полноэкранным контролом `BACK` (закрытие касанием в любом месте).
Отрисовка — в `lcd/tft/ui_320x480.cpp` (по образцу `draw_kill_screen()`,
строки 150-173); данные берутся из `print_session.last_event()`.

**Обоснование.**
- В этом UI нет композитинга: `CANVAS::SetBackground()` заливает весь canvas
  (`lcd/tft/canvas.cpp:52-64`), альфа-канала нет → настоящий полупрозрачный
  оверлей невозможен. Требование «модальное окно поверх текущего экрана»
  реализуется стеком экранов: новый экран непрозрачен, закрытие возвращает
  на статус-экран (фактическое поведение `ui.abort_print()` →
  `return_to_status()`; `screen_history`, `menu/menu.cpp:60-109`).
- Нельзя рисовать поверх статус-экрана контролом `CLICK`: `status_screen()`
  перехватывает клик и уводит в `menu_main` (`lcd/marlinui.cpp:667-675`).
- Возврат ровно на исходный экран потребовал бы отдельного сохранения стека
  TFT до `return_to_status()`; текущий контракт фиксирует возврат в статус.

**Отклонено.** `MenuItem_confirm::select_screen()` (полноэкранный шаблон
меню, но с фиксированной геометрией «да/нет» и без многострочного текста);
`ui.set_status()` (одна строка в статус-баре, не «модальное окно» и легко
перетирается).

Показ не выполняется при `marlin_state == MF_KILLED` (приоритет аварийного
экрана, FR-002) и при `wait_for_user` (активный диалог паузы), а также для
событий, синтезированных при загрузке: сброс виден в журнале (US1 сценарий 2).

## R10. Экран журнала: новое меню, доступ за 2 касания

**Решение.** `Marlin/src/lcd/menu/menu_journal.cpp`, пункт
`SUBMENU(MSG_STOP_JOURNAL, menu_journal)` в `menu_configuration()`
(`lcd/menu/menu_configuration.cpp`) сразу после `BACK_ITEM` (до
`ADVANCED_SETTINGS`), чтобы на 320×480 он был виден без прокрутки. В списке —
по две строки на событие
(`#NN причина источник MM:SS` и `файл P%`), новые сверху, пустой журнал —
`MSG_STOP_JOURNAL_EMPTY`.

**Обоснование.**
- FR-016: чтение только с экрана; SC-007: не более 2 действий с главного
  экрана — иконка «Настройки» на статус-экране (`ui_320x480.cpp:438-506`) плюс
  пункт меню.
- Новый файл в `src/lcd/menu` попадает в сборку через
  `HAS_MARLINUI_MENU = src_filter=+<src/lcd/menu>` (`ini/features.ini:56`) и
  отсутствует в списке исключений `platformio.ini:57-80`; правка конфигурации
  сборки не нужна (проверяется сборкой).
- `START_MENU()`/`STATIC_ITEM_F` уже используются в `menu_info.cpp:54-97` для
  списков; прокрутка и касания работают штатно.

**Отклонено.** Отдельная иконка на статус-экране (1 касание, но правка
навигации главного экрана — риск регрессии, принцип VI); вывод журнала в
консоль/сеть (прямо исключено FR-016).

## R11. Локализация

**Решение.** Новые `LSTR MSG_*` в `lcd/language/language_en.h` и
`language_ru.h`; в коде — `GET_TEXT_F(MSG_...)`; тексты причин выбираются
функцией `switch`, возвращающей `FSTR_P` (а не статическим массивом), чтобы
смена языка (`ui.set_language`) применялась сразу.

**Обоснование.** `language_ru.h` содержит `using namespace Language_en`, т.е.
непереведённая строка автоматически берётся из английского — обязателен только
EN-вариант, RU добавляем для всех новых строк (FR-011). TFT-шрифт содержит
кириллицу (`DISPLAY_CHARSET_RUS`, `fontdata/helvetica_18.cpp`), `TFT_String`
конвертирует UTF-8.

**Отклонено.** Хардкод русских строк в TFT-коде (нарушает принцип VI);
`PROGMEM`-массив `FSTR_P` (не обновляется при смене языка без перерисовки).

## R12. Флаг фичи и параметры

**Решение.** В `Configuration_adv.h` — блок `@section FB-G6: print session
journal`:

```cpp
#define FB_G6_PRINT_JOURNAL                  // Журнал причин остановки печати
#if ENABLED(FB_G6_PRINT_JOURNAL)
  #define FB_G6_PRINT_JOURNAL_SLOTS      16   // 1..32
  #define FB_G6_PRINT_JOURNAL_REGION    768   // байт в конце EEPROM
  #define FB_G6_PRINT_JOURNAL_CHECKPOINT_S 300 // с, 0 = только старт/стоп
  #define FB_G6_PRINT_JOURNAL_MODAL           // Модальное окно причины
  #define FB_G6_SD_READ_ERROR_LIMIT      3    // подряд ошибок чтения до останова
#endif
```

**Обоснование.** Принципы II и III: кастома — под `FB_G6_*`, значения — в
конфиге в стиле Marlin (`@section`, комментарий, допустимые значения).
Флаг включён по умолчанию, т.к. это требование продукта для FB-G6; при
выключенном флаге модуль не содержит кода, а вставки в общие файлы исчезают.

**Отклонено.** Отдельный `build_params.h`-вариант (термистор/BLTouch — не та
ось); флаг в `platformio.ini` (не соответствует стилю репозитория).

## R13. Что НЕ делаем

- Не меняем формат MKS WiFi и не добавляем команды чтения журнала (FR-016).
- Не добавляем `new`/`delete`, SD-лог, облако, RTC, полноценный лог на носителе.
- Не трогаем пороги thermal protection, watchdog, `SanityCheck` (кроме новой
  проверки `EEPROM_SETTINGS`), software endstops (FR-013, принцип I).
- Не меняем поведение остановки: нагрев выключается, по отмене выполняется
  `EVENT_GCODE_SD_ABORT "G28XY"` (`Configuration_adv.h:1565`), Z не меняется,

## R14. «Карта стала недоступна»: эскалация ошибок чтения до останова

**Решение.** В `gcode/queue.cpp::get_sdcard_commands()` (строки 562-565) рядом с
существующим `SERIAL_ERROR_MSG(STR_SD_ERR_READ)` добавить счётчик подряд идущих
ошибок чтения; при `FB_G6_SD_READ_ERROR_LIMIT` (по умолчанию 3) — метка
`SOURCE_MEDIA` и `card.abortFilePrintSoon()`; успешное чтение сбрасывает
счётчик.

**Обоснование.** В этом форке нет `SDCARD_READ_ERROR`-логики: ошибка чтения
байта только печатается в serial и чтение продолжается («continue»), а
извлечение карты обрабатывается лишь через `HAS_SD_DETECT` →
`CardReader::release()` (`sd/cardreader.cpp:538-551`). US1 сценарий 5 требует
остановки с причиной «ошибка носителя» и при «становится недоступна», поэтому
без счётчика часть дефектов (умирающая карта, плохой контакт) останется
«немой». Три подряд идущих ошибки — компромисс: одиночный сбой не рвёт печать,
устойчивая деградация — рвёт.

**Отклонено.** Остановка по первой же ошибке (ложные срабатывания на границе
файла/буфера); периодические проверки `Sd2Card::errorCode()` (не связаны с
потоком чтения, который идёт через `FAT`/`SdFile::read`); таймаут «нет данных
N секунд» (печать может законно стоять на нагреве).

**Ограничение.** Счётчик не пишет в EEPROM и не влияет на темп: проверка уже
выполняется на каждый читаемый байт, добавление — инкремент/сброс `uint8_t`.
