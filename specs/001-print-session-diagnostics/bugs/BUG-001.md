# Bug Report: Перезагрузка по watchdog при показе экрана причины останова

**Type**: Implementation drift
**Severity**: Critical
**Feature**: `001-print-session-diagnostics`
**Reported**: 2026-11-04
**Status**: Patched
**Patched**: 2026-11-04
**Verified**: 2026-11-04 — исправление проверено на принтере (STOP в нагреве и во время печати, журнал остановок)
**Build**: `FBG6-2.1.2.8-104gt` (Nov 4 2026, `FB_G6_EEPROM_LAYOUT_ID 0x18511780`)
**Hardware**: MKS Robin Nano V3 + MKS TS35 V2.0, прошивка на принтере

## Description

При остановке печати кнопкой STOP на экране принтер вместо модального окна
причины **перезагружается**: экран гаснет, плата стартует заново со штатным
звуковым сигналом. Печать при этом фактически отменяется (нагреватели
выключаются, движение прекращается), но пользователь не видит причину
останова — основную функцию US1 — и получает внезапную перезагрузку.

По USB-консоли зафиксирован сброс с причиной `Watchdog Reset`: прошивка
зависает примерно на 4 секунды (период сторожевого таймера) в обработчике
останова, после чего IWDG перезагружает MCU.

### Условия воспроизведения

1. Прошивка с `FB_G6_PRINT_JOURNAL` и `FB_G6_PRINT_JOURNAL_MODAL`.
2. Запуск печати с SD-карты (`M23 <файл>` + `M24` либо выбор файла на экране).
3. Нажатие STOP на экране (иконка «СТОП») в любой момент печати, в том числе
   во время нагрева.
4. Принтер отменяет печать, затем зависает и перезагружается по watchdog.

### Лог (метки `DBG:` временной диагностической сборки)

```text

12.0s DBG: abort: begin
12.0s DBG: abort: queued
12.0s //action:cancel
12.0s DBG: abort: hostui
12.0s DBG: abort: msg
12.0s DBG: abort: status
12.0s DBG: stop: abort_print
12.0s DBG: clear: begin ... DBG: clear: fill
12.0s DBG: stop: clear_lcd
12.0s DBG: sd: begin

12.2s DBG: sd: card
```

Метка `DBG: modal: synced` (сразу после `tft.queue.sync()`) не появляется:
зависание происходит внутри синхронной отрисовки экрана причины.

## Root Cause Analysis

В `TFT_COLOR_UI` (Marlin `lcd/tft/tft_queue.cpp`) операции рисования работают
не с отдельными «примитивами», а с **задачами очереди**:

- `tft.fill()` создаёт задачу `TASK_FILL`, записывает параметры, а сразу за
  ними — маркер `TASK_END_OF_QUEUE`, на который указывает `nextTask` задачи;
- `tft.add_text()` / `tft.add_rectangle()` / `tft.set_background()` **не
  создают задачу**, а дописывают параметры в `end_of_queue` и увеличивают
  счётчик элементов **последней** задачи (той, что создана
  `tft.canvas()`/`tft.fill()`).

`stop_reason_screen()` делал так:

```cpp
tft.queue.reset();
tft.fill(0, 0, TFT_WIDTH, TFT_HEIGHT, COLOR_BACKGROUND);  // задача TASK_FILL + маркер конца
...
tft.add_text(...);        // параметры записываются ПОВЕРХ маркера конца
tft.add_rectangle(...);   // и далее
tft.queue.sync();
```

Параметры текста (`CANVAS_ADD_TEXT`, `x`, `y`, …) затирают байт
`TASK_END_OF_QUEUE`. После завершения заливки `TFT_Queue::async()` берёт
`nextTask` — а там уже не маркер, а параметры текста, которые интерпретируются
как `queueTask_t {type, state, nextTask}` с мусорными значениями. Задача не
переходит в состояние `TASK_STATE_COMPLETED`, и `TFT_Queue::sync()`
(`while (current_task != nullptr) async();`) крутится бесконечно — при этом
`tft.is_busy()` может оставаться `true` после DMA с нулевой/мусорной длиной.
Цикл не обновляет сторожевой таймер → через ~4 с IWDG перезагружает плату.

Почему это не поймали раньше:

- остальные экраны (`draw_status_screen()`, `menu_line()`, `draw_kill_screen()`
  через `menu_line()`) создают canvas-задачу перед текстом, поэтому схема
  работает; `stop_reason_screen()` — единственное место, где после `fill()`
  добавлены текст и линии без canvas;
- контракт `contracts/ui-contract.md` §1.3 требовал canvas, но проверка
  соответствия кода контракту не была формализована;
- ручные проверки на принтере (**T034**, **T039**, **T045**, **T050**)
  оставались открытыми, а первый же сценарий останова (S1/S12) выявил дефект;
- `pio run` и статический анализ такое не обнаруживают: дефект — логика
  очереди в рантайме.

Замечание о воспроизводимости: в том же прогоне остановка из консоли (`M524`,
источник «консоль») зависания не дала — состояние TFT-очереди к моменту показа
окна отличается (другой текущий экран и другая последовательность
`clear_lcd()`), поэтому мусорная задача в этом прогоне не сложилась.
Дефект в отрисовке детерминирован и не зависит от источника останова, поэтому
исправление обязательно и для пути `M524`.

## Recommended Fix

1. **Код** (уже подготовлен, не закоммичен): в
   `Marlin/src/lcd/tft/ui_320x480.cpp::stop_reason_screen()` заменить

   ```cpp
   tft.fill(0, 0, TFT_WIDTH, TFT_HEIGHT, COLOR_BACKGROUND);
   ```

   на

   ```cpp
   tft.canvas(0, 0, TFT_WIDTH, TFT_HEIGHT);
   tft.set_background(COLOR_BACKGROUND);
   ```

   с комментарием «почему»: текст и линии пишутся в последнюю задачу, поэтому
   фон обязан быть canvas-задачей, иначе маркер конца очереди затирается и
   цепочка задач разрушается.

2. `/speckit.bugfix.patch` — обновить артефакты:
   - `spec.md`: добавить проверяемое условие приёмки «показ экрана причины не
     приводит к зависанию UI и сбросу по watchdog» (FR-002/FR-013, SC-001);
   - `plan.md`: в Фазе C п. 14 зафиксировать требование canvas-задачи; добавить
     риск R8 (порча очереди TFT при ручной отрисовке);
   - `contracts/ui-contract.md`: §1.3 — усилить формулировку («фон обязан быть
     canvas-задачей; `tft.fill()` перед `add_text()` запрещён»);
   - `tasks.md`: переоткрыть T030, добавить T055 (исправление) и T056
     (проверка на принтере).
3. `/speckit.bugfix.verify` — проверить согласованность артефактов.
4. `/speckit.implement` — внести исправление, пересобрать
   `mks_robin_nano_v3`, прошить и пройти STOP-сценарий на принтере
   (в нагреве и во время печати), затем остановку из консоли `M524`.

## Заметки о влиянии

- EEPROM-раскладка, `SettingsData`, `EEPROM_VERSION` и
  `FB_G6_EEPROM_LAYOUT_ID` не затрагиваются — настройки пользователя при
  перепрошивке сохраняются, `Initialize EEPROM` не требуется.
- Журнал остановок не затрагивается: событие об отмене записывается до показа
  окна (`DBG: sd: journal` в логе), то есть данные не терялись и при
  перезагрузке.
- Защиты не ослабляются; наоборот, устраняется ложное срабатывание IWDG.
