# Clean C++: полный справочник

Адаптация каталога Clean Code (Robert C. Martin, глава 17) под C++ и прошивку
Marlin. При конфликте с [Marlin Coding Standards](https://marlinfw.org/docs/development/coding_standards.html)
и стилем репозитория побеждает стиль репозитория.

## Comments (C1-C5)

- **C1** — никаких метаданных в комментариях (автор, дата, номер тикета): для
  этого есть Git.
- **C2** — устаревший комментарий удалять сразу, а не «потом».
- **C3** — не пересказывать код комментарием. Комментарий объясняет **почему**.
- **C4** — если комментарий нужен, писать его грамотно и кратко.
- **C5** — закомментированный код не коммитить.

## Environment (E1-E2)

- **E1** — сборка одной командой: `pio run -e mks_robin_nano_v3`.
- **E2** — проверки одной командой: `make tests-single-local TEST_TARGET=...`.

## Functions (F1-F4)

- **F1** — не больше 3 аргументов. Больше — структура/класс с именованными
  полями.
- **F2** — никаких выходных аргументов через указатель, если можно вернуть
  значение.
- **F3** — никаких булевых флагов-аргументов: функция с флагом делает два дела.
- **F4** — мёртвые функции удалять, Git всё помнит.

```cpp
// Плохо: 6 аргументов и флаг
void draw_status(const char *title, const char *value, int16_t x, int16_t y,
                 uint16_t color, bool inverted);

// Хорошо: одна структура
struct StatusLine {
  const char *title;
  const char *value;
  int16_t x, y;
  uint16_t color;
};
void draw_status(const StatusLine &line);
```

## General (G1-G36)

- **G1** — один язык на файл.
- **G2** — реализовывать ожидаемое поведение, а не удобное.
- **G3** — обрабатывать граничные условия.
- **G4** — не обходить защитные механизмы (thermal protection, watchdog,
  software endstops, sanity checks).
- **G5** — DRY: у знания одно авторитетное представление.
- **G6** — не смешивать уровни абстракции в одной функции.
- **G7** — базовый класс не знает о наследниках.
- **G8** — минимизировать публичный интерфейс.
- **G9** — удалять мёртвый код.
- **G10** — объявлять переменную рядом с местом использования.
- **G11** — быть последовательным.
- **G12** — убирать информационный шум.
- **G13** — не создавать искусственных связей между модулями.
- **G14** — не завидовать чужому состоянию (feature envy).
- **G15** — не передавать «селектор» поведения аргументом.
- **G16** — не прятать намерение за «умным» кодом.
- **G17** — код там, где его ожидают найти.
- **G18** — предпочитать методы класса свободным функциям, если есть состояние.
- **G19** — вводить поясняющие переменные.
- **G20** — имя функции говорит, что она делает.
- **G21** — понимать алгоритм, а не копировать его вслепую.
- **G22** — зависимости делать явными (include, параметры), а не скрытыми.
- **G23** — полиморфизм предпочтительнее длинных `if/else` по типу.
- **G24** — следовать конвенциям языка и линтеру/форматтеру.
- **G25** — именованные константы вместо магических чисел.
- **G26** — быть точным: типы, единицы измерения, знаки.
- **G27** — структура важнее договорённостей «на словах».
- **G28** — инкапсулировать сложные условия в именованные предикаты.
- **G29** — избегать отрицательных условий (`if (!notReady)`).
- **G30** — функция делает одно дело.
- **G31** — временны́е связи делать явными (порядок вызовов, init).
- **G32** — не быть произвольным: одинаковые вещи — одинаково.
- **G33** — инкапсулировать граничные условия.
- **G34** — один уровень абстракции на функцию.
- **G35** — конфигурация — на верхнем уровне, а не в глубине кода.
- **G36** — Law of Demeter: не тянуть цепочки `a.b.c.d`.

```cpp
// Плохо: магическое число и скрытая единица измерения
if (ms > 86400) { /* ... */ }

// Хорошо: имя и единица видны
constexpr uint32_t SECONDS_PER_DAY = 86400;
if (elapsed_seconds > SECONDS_PER_DAY) { /* ... */ }
```

## Names (N1-N7)

- **N1** — имя раскрывает намерение.
- **N2** — имя соответствует уровню абстракции.
- **N3** — использовать стандартную терминологию предметной области.
- **N4** — имя однозначно (`rename_file(old_path, new_path)`, а не
  `rename(source, target)`).
- **N5** — длина имени соответствует области видимости.
- **N6** — без венгерской нотации и префиксов типа (`str_name`, `arr_users`).
- **N7** — имя описывает побочные эффекты (`get_or_create_config`).

В Marlin: `snake_case` для функций и переменных, `PascalCase` для классов,
`SCREAMING_SNAKE_CASE` для макросов, суффикс `_t` для структур.

## C++-specific (CPP1-CPP6)

- **CPP1 — RAII и статическая память.** Новый код не использует `new`/`delete` и
  динамическое выделение в рантайме. Объекты — статические или на стеке, буферы —
  фиксированного размера. Единственное известное исключение — сортировка SD при
  `SDSORT_DYNAMIC_RAM` в `cardreader.cpp`; не расширять его без необходимости.
- **CPP2 — const-correctness.** `const`, `constexpr`, `const_float_t` для
  аргументов, которые не меняются; константные методы.
- **CPP3 — макросы только для конфигурации.** Для логики — `inline`-функции,
  `constexpr`, шаблоны. Макросы семейства `ENABLED()` — часть стиля Marlin,
  их не «оптимизировать».
- **CPP4 — типы фиксированной ширины.** `uint8_t`, `int16_t`, `uint32_t` там,
  где важен размер; избегать неявного сужения.
- **CPP5 — без исключений и RTTI.** Ошибки — коды возврата, проверки,
  `SERIAL_ERROR_MSG`. На MCU нет места для раскрутки стека.
- **CPP6 — дисциплина flash/RAM.** Строки — через `F("...")`, таблицы — через
  `PROGMEM`, большие буферы — не на стеке (маленький stack у ISR).

## Tests (T1-T9)

- **T1** — проверять всё, что может сломаться.
- **T2** — использовать инструменты покрытия как ориентир, не как цель.
- **T3** — не пропускать «тривиальные» проверки: они документируют поведение.
- **T4** — пропущенный тест — это вопрос о неоднозначности, а не решение.
- **T5** — проверять границы: 0, максимум, пустой буфер, переполнение.
- **T6** — найден баг — проверить все похожие случаи.
- **T7** — искать паттерн в падениях.
- **T8** — смотреть, какие ветки не покрыты: часто это признак плохого дизайна.
- **T9** — проверки должны быть быстрыми и воспроизводимыми.

В этом репозитории «тест» — это сборка эталонной конфигурации:

```bash
pio run -e mks_robin_nano_v3
make tests-single-local TEST_TARGET=mks_robin_nano_v1v2
```

## Антипаттерны (не надо → надо)

| ❌ Не надо | ✅ Надо |
| --- | --- |
| Комментировать каждую строку | Удалить очевидные комментарии |
| `#define MAX(a,b) ((a)>(b)?(a):(b))` | `inline`/`constexpr`-функция или `MAX()` из Marlin |
| `new uint8_t[size]` | Статический буфер + проверка границ |
| Магическое `86400` | `constexpr uint32_t SECONDS_PER_DAY` |
| `process(data, true)` | `process_verbose(data)` |
| Глубокая вложенность | Ранние возвраты, guard clauses |
| `obj.a.b.c.value` | `obj.get_value()` |
| Функция на 200 строк | Разбить по ответственности |
| `Serial.print` внутри ISR | Флаг + обработка в основном цикле |

## Поведение агента

- При ревью указывать номер правила: «G5: дублирование логики».
- При правке сообщать, что исправлено: «G25: вынес `86400` в
  `SECONDS_PER_DAY`».
- Не делать рефакторинг, не связанный с задачей: одно-два небольших улучшения
  в затронутом коде, не больше.
